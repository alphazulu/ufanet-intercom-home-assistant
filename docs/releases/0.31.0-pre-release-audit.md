## Authorized devices and advanced FCM

### Disposition: complete for current release validation

Live-confirmed provider model:

- a plain Ufanet JWT session created by `auth_by_contract` can query `POST /api/v4/fcm_device/authorized_devices/` without registering for FCM;
- `last_update` is treated as provider activity time, not login time;
- the inventory is coupled to device/FCM registration state and is **not** an exhaustive independent inventory of every JWT;
- a plain-JWT controller can revoke another test device through `POST /api/v4/fcm_device/logout_device/`;
- after `logout_device`, the target row disappears, the target's already-issued access JWT can remain accepted, and its refresh JWT is rejected with HTTP 401; an independent observer/controller remains authorized;
- direct `DELETE /api/v0/fcm/` without `logout_device` also removes the target row and invalidates the tested target refresh JWT while the already-issued access JWT can remain temporarily usable; an independent observer remains authorized.

Canonical Home Assistant service split:

```text
list_authorized_devices
revoke_authorized_device
revoke_other_authorized_devices

list_fcm_registrations
unregister_fcm_registration
unregister_other_fcm_registrations
```

Legacy compatibility aliases remain:

```text
list_fcm_sessions
revoke_fcm_session
revoke_other_fcm_sessions
```

The legacy revoke names still call `logout_device`; they are not direct FCM unregister operations.

Safety/privacy controls:

- public selection uses opaque `authorization_ref` / `fcm_ref` values;
- raw provider `device_id` and FCM token values are not exposed;
- Home Assistant-owned registrations are protected only when ownership can be proven from private local state;
- ownership verification fails closed before destructive actions;
- targeted actions refresh/resolve the inventory before mutation;
- bulk operations require an exact expected target count and abort when the inventory changes;
- advanced FCM cleanup explicitly warns that the tested refresh authorization is invalidated.

Frontend live validation confirmed successful removal of test entries from the **УСТРОЙСТВА / DEVICES** UI and the separate advanced FCM section while the locally owned Home Assistant registration remained protected.

## Physical keys

### Capability / inventory / history: complete

Live-confirmed:

- account/intercom physical-key capability;
- empty and non-empty key inventory;
- real key fields `id`, `external_id`, `name`, `create_date`, `devices`;
- empty and non-empty passage history;
- real passage fields `key:str`, `key_name:str`, `time_passage:int`;
- selected-key history through `filters.key=<external_id>`;
- Home Assistant/Lovelace selected-key passage rendering;
- later passage updates continued to correlate to the same physical key.

### Identifier semantics: resolved

A direct comparison proved that the printed number on the tested physical key does **not** match `external_id` or the other tested provider identifier candidates. `external_id` remains private and is used only as the confirmed backend history selector. No guessed printed-key number is exposed publicly.

### Rename: complete for tested success path

Live-confirmed:

- `POST /api/v4/key/edit/` changes the selected key name;
- provider read-back is eventually consistent;
- runtime sends one state-changing write only;
- bounded read-only verification retries observe the updated name;
- automatic post-write verification succeeds without a manual refresh.

### Enrollment: HARD RELEASE BLOCKER

Still required with a genuinely unregistered physical key:

1. press **Add physical key** and verify `POST /api/v4/key/skud/<id>/auto_collect/enable/` really arms enrollment;
2. present the new key within the observed 60-second window;
3. verify the physical key is actually registered;
4. capture a real sanitized `reason=key_add` completion and verify the observed `key_status` / `key_id` contract;
5. verify FCM-triggered inventory refresh updates the numeric key count and privacy-safe read surfaces promptly;
6. verify `ufanet_intercom_key_enrollment` reports the correct privacy-minimized result;
7. inspect real enrollment error behavior, including any observed HTTP 400/status semantics.

Until this is completed or explicitly waived with a documented reason, do not merge/tag/publish 0.31.0.

### Key deletion: outside 0.31.0 scope

The Android-observed key-delete endpoint remains unimplemented and not live-validated. It is a destructive access-control operation and is not a release blocker because it is deliberately excluded from this release scope.

## Frontend / packaging audit

The validation branch packages the base card and extensions for physical keys, key history, and authorized-device/advanced-FCM management.

Audit finding fixed:

- the previous release self-check parsed only the base card and enforced only the base card cache-bust;
- the hardened release check now runs `node --check` for every packaged frontend `.js` file;
- it scans `_callResponseService(...)` references from every frontend file against `services.yaml`;
- it enforces synchronized cache-bust versions for all packaged extensions.

This prevents a release candidate from passing while a browser extension remains pinned to an older release resource.

## Privacy audit

Current public/runtime boundaries retained:

- no Ufanet password/access/refresh JWT in entities, frontend, diagnostics, or docs;
- no UCAMS bearer token or tokenized media URLs in persistent public state;
- no FCM/GCM token, Firebase installation credential, or raw push payload in public diagnostics/docs;
- no raw provider authorized-device `device_id` in browser-facing management responses;
- no provider physical-key `id`, `key_id`, or `external_id` in public key-management surfaces;
- no guessed physical-key number;
- notification door actions remain bound to the selected Home Assistant device and explicit user intent;
- destructive device/FCM actions require explicit confirmation and protected-ownership checks.

## Final release-candidate procedure

After the physical-key enrollment gate is complete or explicitly waived:

1. update enrollment evidence labels/docs/CHANGELOG from the actual live result;
2. obtain explicit approval to prepare the release candidate;
3. bump all release-facing versions/cache-busts listed above to the agreed version in one synchronized change;
4. run `python scripts/release_check.py --strict-hacs`;
5. require Tests, HACS/Hassfest, and Release self-check to succeed on the **exact** candidate SHA;
6. perform one final secrets/privacy diff review;
7. obtain separate explicit approval before merge;
8. obtain separate explicit approval before tag/GitHub Release.

Existing release tags are immutable and must not be moved.
