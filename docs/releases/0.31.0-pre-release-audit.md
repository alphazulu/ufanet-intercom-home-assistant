## Authorized devices and advanced FCM

### Disposition: complete for current release validation

Live-confirmed provider model:

- a plain Ufanet JWT session created by `auth_by_contract` can query `POST /api/v4/fcm_device/authorized_devices/` without registering for FCM;
- the inventory is coupled to device/FCM registration state and is not an exhaustive independent inventory of every JWT;
- a plain-JWT controller can revoke another test device through `POST /api/v4/fcm_device/logout_device/`;
- after `logout_device`, the target row disappears, an already-issued access JWT can remain accepted, and the target refresh JWT is rejected with HTTP 401; an independent observer remains authorized;
- direct `DELETE /api/v0/fcm/` without `logout_device` also removes the target row and invalidates the tested target refresh JWT while an already-issued access JWT can remain temporarily usable.

Canonical Home Assistant service split:

```text
list_authorized_devices
revoke_authorized_device
revoke_other_authorized_devices

list_fcm_registrations
unregister_fcm_registration
unregister_other_fcm_registrations
```

Legacy `*_fcm_sessions` names remain compatibility aliases for the `logout_device` path.

The **DEVICES / УСТРОЙСТВА** UI and separate advanced FCM section were live-tested. Raw provider device IDs and FCM tokens are not exposed, and locally provable Home Assistant registrations remain protected.

## Physical keys

### Capability / inventory / history: complete

Live-confirmed:

- account/intercom physical-key capability;
- empty and non-empty key inventory;
- real key fields `id`, `external_id`, `name`, `create_date`, `devices`;
- empty and non-empty passage history;
- real passage fields `key:str`, `key_name:str`, `time_passage:int`;
- selected-key history through `filters.key=<external_id>`;
- Home Assistant/Lovelace selected-key passage rendering and later updates.

### Identifier semantics: resolved

The printed number on the tested physical key does not match `external_id` or the other tested provider identifier candidates. `external_id` remains private and is used only as the confirmed backend passage-history selector. No guessed printed-key number is exposed publicly.

### Rename: complete for tested success path

Live-confirmed:

- `POST /api/v4/key/edit/` changes the selected key name;
- provider read-back is eventually consistent;
- runtime sends one state-changing write only;
- bounded read-only verification retries observe the updated name;
- automatic post-write verification succeeds without manual refresh.

### Enrollment: complete for current release validation

A genuinely unregistered physical key was successfully enrolled end to end through Home Assistant.

Live-confirmed successful path:

1. **Add physical key** invoked the Android-observed `POST /api/v4/key/skud/<id>/auto_collect/enable/` flow;
2. the intercom entered the expected 60-second enrollment window;
3. a previously unregistered key was presented and was actually registered;
4. the active headless FCM listener received real `reason=key_add` completion pushes;
5. diagnostics recorded two real key-add pushes and `last_key_add_result=success` while FCM was active and fallback polling was inactive;
6. the success classification therefore matched the Android-observed `key_status == 0` plus parseable `key_id` rule;
7. the physical-key coordinator remained healthy and the registered-key inventory was present after enrollment.

A separate no-key timeout test armed the same 60-second window and deliberately presented no key. After the complete window elapsed, no additional `reason=key_add` completion push arrived and the previous success counters/result remained unchanged.

Therefore the tested timeout behavior is:

```text
arm enrollment
→ wait 60 seconds without a key
→ enrollment window expires
→ no key_add completion push observed
```

No HTTP 400, `key_status != 0`, or separate FCM error completion was observed in this timeout case. Those unobserved provider error semantics are not inferred and are not a release requirement.

Detailed sanitized evidence is recorded in:

`docs/api/key_enrollment_live_2026-09-09.md`

**Disposition: the former physical-key enrollment hard functional blocker is CLOSED.**

### Key deletion: outside 0.31.0 scope

The Android-observed key-delete endpoint remains unimplemented and not live-validated. It is a destructive access-control operation and is deliberately excluded from 0.31.0, so it is not a release blocker.

## Frontend / packaging audit

The validation branch packages the base card plus extensions for physical keys, key history, and authorized-device/advanced-FCM management.

The release self-check now:

- runs `node --check` for every packaged frontend `.js` file;
- scans `_callResponseService(...)` references from every frontend file against `services.yaml`;
- enforces synchronized cache-bust versions for every packaged extension.

This prevents an RC from passing while a browser extension remains pinned to an older resource version.

## Privacy audit

Current boundaries retained:

- no Ufanet password/access/refresh JWT in entities, frontend, diagnostics, or docs;
- no UCAMS bearer token or tokenized media URL in persistent public state;
- no FCM/GCM token, Firebase installation credential, or raw push payload in public diagnostics/docs;
- no raw provider authorized-device `device_id` in browser-facing management responses;
- no provider physical-key `id`, `key_id`, or `external_id` in public key-management surfaces;
- no guessed physical-key number;
- notification door actions remain bound to the selected Home Assistant device and explicit user intent;
- destructive device/FCM actions require confirmation and protected-ownership checks.

## Release-candidate procedure

The project is now eligible for release-candidate preparation, but the version bump is a separate release action and still requires explicit user approval.

After that approval:

1. update remaining EN/RU enrollment evidence labels from Observed to Confirmed and synchronize CHANGELOG/release notes;
2. bump every release-facing version/cache-bust listed above to `0.31.0` in one synchronized change;
3. run `python scripts/release_check.py --strict-hacs`;
4. require Tests, HACS/Hassfest, and Release self-check to succeed on the exact RC SHA;
5. perform one final secrets/privacy/documentation consistency review;
6. obtain separate explicit approval before merge;
7. obtain separate explicit approval before tag/GitHub Release.

Existing release tags are immutable and must not be moved.
