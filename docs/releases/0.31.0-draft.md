# Ufanet Intercom 0.31.0 — draft release notes

> **DRAFT / NOT FOR PUBLICATION YET.** This document prepares the future release text. It does not authorize merge, tag or GitHub Release. PR #15 hard live-validation gates remain authoritative.

## Highlights

### Actionable incoming-call notifications

The Home Assistant Companion notification workflow has been expanded from passive call alerts to guarded actions:

- immediate text notification for a confirmed Ufanet call;
- private Home Assistant image replacement when the cached last-call JPEG becomes ready;
- optional **Open door** action restricted to the selected Ufanet device and revalidated immediately before `button.press`;
- **View camera** navigation to the selected same-device live camera;
- stable per-intercom notification tags and timeout-based removal of stale door actions;
- manual blueprint runs deliberately contain no physical door action.

Android real-call delivery, physical door opening, live-camera navigation and timeout replacement have been live-tested. Additional live validation confirmed that a second real call supersedes the first pending notification/action, the resulting notification shows the expected device/location/time metadata, and after a successful **Open door** action the same notification is replaced without creating a duplicate and without leaving the old door action available.

The only notification case that could not be performed literally was a negative test using a second Ufanet device. A targeted security/code review confirmed layered cross-device isolation: exact device-trigger filtering, same-device button membership before exposing the action, the same membership revalidation immediately before `button.press`, unique per-call action IDs, `mode: restart`, and no provider target identifier coming from the phone. The missing second-device **live test only** is explicitly waived and documented in `docs/notification_cross_device_security_review_2026-09-07.md`; the safety invariant itself is not waived.

iOS action delivery is not yet live-tested and is not described as such.

### Authorized devices and advanced FCM management

The validation branch now separates the official Ufanet device-authorization action from direct FCM cleanup instead of treating both as generic “FCM sessions”.

Canonical Home Assistant response services are:

```text
list_authorized_devices
revoke_authorized_device
revoke_other_authorized_devices

list_fcm_registrations
unregister_fcm_registration
unregister_other_fcm_registrations
```

The historical `list_fcm_sessions`, `revoke_fcm_session`, and `revoke_other_fcm_sessions` names remain compatibility aliases. Their revoke operations use `logout_device`; new automations should use the canonical authorized-device names.

Controlled live tests established the authorization semantics:

- a plain Ufanet JWT controller that never registered for FCM can query `authorized_devices`;
- that plain-JWT controller can revoke a different test device through `POST /api/v4/fcm_device/logout_device/`;
- after `logout_device`, the target row disappears, its already-issued access JWT can remain accepted, and its refresh JWT is rejected with HTTP 401; an independent observer/controller remains authorized;
- a separate disposable-device probe called only `DELETE /api/v0/fcm/`, never `logout_device`; the target row again disappeared, its existing access JWT remained temporarily usable, and its refresh JWT was rejected with HTTP 401 while the independent observer survived.

These results mean `authorized_devices` is the provider **device/registration inventory used by the active-device UI**, not an exhaustive independent list of every JWT. They also mean direct FCM unregister is authorization-destructive for the tested refresh chain and must not be described as a harmless push unsubscribe.

The **УСТРОЙСТВА / DEVICES** Lovelace tab now uses canonical authorized-device services for normal revoke operations. A separate collapsed **advanced FCM** section exposes direct unregister with an explicit authorization warning. Raw provider `device_id` values and FCM tokens are never returned to the frontend; opaque `authorization_ref` / `fcm_ref` handles are used instead. Locally provable Home Assistant-owned registrations remain protected and destructive ownership checks fail closed.

This UI was live-tested: test entries were removed successfully and the locally owned Home Assistant registration remained protected.

### Physical keys and passage history

For intercoms advertising physical-key recording support, the validation branch adds:

- numeric **Physical keys** sensor and read-only inventory;
- **Last key passage** timestamp;
- passage EventEntity, Home Assistant event and visual device trigger;
- **КЛЮЧИ / KEYS** Lovelace tab;
- selected-key passage history loaded below the key list;
- privacy-safe `list_physical_keys` and `get_physical_key_passages` response services;
- validation-only **Add physical key** and **Rename** workflows;
- FCM `reason=key_add` completion handling with immediate inventory refresh.

Live-confirmed read-only behavior includes a non-empty key inventory, the real passage schema (`key:str`, `key_name:str`, `time_passage:int`), selected-key filtering with `filters.key=<external_id>`, and real passage timestamps rendered end to end in Lovelace.

### Physical-key identifier semantics resolved

The official Android client uses physical-key `external_id` when requesting history for one selected key. Live testing confirmed that this selector continues to return the correct updating history for the tested physical key.

A direct comparison also showed that the number printed on that physical key does **not** match `external_id` or the other candidate identifier values returned by the tested key-list response. The project therefore no longer exposes those provider values as a guessed physical-key number.

`list_physical_keys` and the KEYS tab expose only the opaque local `key_ref`, user-facing name and creation time. Provider `id` and `external_id` stay private runtime data.

### Physical-key enrollment remains validation-only; rename is live-confirmed

The Android-observed enrollment flow uses:

```text
POST /api/v4/key/skud/<id>/auto_collect/enable/
```

and opens a 60-second enrollment window. The real new-key side effect and `reason=key_add` push have not yet been live-confirmed.

The rename flow uses:

```text
POST /api/v4/key/edit/
```

A controlled Home Assistant live test confirmed that the endpoint really changes the selected physical key name. Ufanet's key inventory is eventually consistent: the first immediate read-back can still contain the previous name, while a later refresh returns the new name. The validation service therefore issues the provider write only once and performs bounded read-only verification retries before reporting `verified: true`. This retry-based verification path was subsequently live-tested successfully without requiring a manual refresh.

Physical-key deletion remains deliberately unimplemented and outside the 0.31.0 release scope.

## Reliability and safety fixes

- separated physical-key capability, inventory and passage-history health so a temporary history failure cannot incorrectly mark a supported intercom as unsupported;
- registered the main Lovelace card and packaged extensions through the race-safe Lovelace resource path; repeated dashboard switches, normal reloads and hard refreshes were live-tested without reproducing the former **Configuration error**;
- added a packaged authorized-device frontend extension that waits for the base custom element and leaves the base card resource/load order intact;
- hardened the release self-check so **all** frontend extension cache-bust versions must match the manifest/integration/card/README release version; previously only the base archive-card cache-bust was enforced;
- hardened JavaScript release validation to run `node --check` on every packaged frontend JS file and verify response-service references from all frontend extensions against `services.yaml`;
- added Android Companion compatibility fixes found during real notification testing;
- completed a targeted notification cross-device security review and documented the explicit live-test waiver without weakening the runtime guards;
- preserved privacy boundaries for provider device IDs, physical-key IDs, FCM credentials, raw push payloads and tokenized media URLs;
- added regression coverage for opaque refs, separated authorization-vs-FCM actions, selected-key history, physical-key frontend safety, eventual-consistent rename verification and release packaging.

## Documentation / API evidence updates

The API reference distinguishes:

- **Confirmed** — directly exercised successfully;
- **Observed** — seen in client code or responses but not fully live-validated;
- **Inferred** — derived behavior requiring validation;
- **Experimental** — intentionally exposed for controlled validation while semantics remain unproven;
- **Not supported** — tested request form that failed.

For state-changing endpoints, HTTP success alone is not treated as proof of the intended physical/account side effect. The former Experimental printed-key-number hypothesis was resolved by live testing and removed from the public surface rather than promoted incorrectly.

The authorization/FCM documentation now records the tested target-token behavior rather than inferring logout solely from row disappearance: both `logout_device` and direct FCM unregister were tested with the target JWT chain, and in both cases the already-issued access token survived the immediate check while the target refresh token was rejected.

## Still required before publication

The notification block, authorized-device/advanced-FCM management block, and physical-key rename path no longer have hard functional release gates. The remaining hard functional validation is exclusively the new physical-key enrollment path:

1. live-test **Add physical key** with a new unregistered key and confirm the provider really arms enrollment mode;
2. present the new key within the 60-second window and verify it is actually registered;
3. capture the real `reason=key_add` completion using sanitized schema/status evidence only;
4. verify the FCM-triggered inventory refresh updates the numeric key count and privacy-safe read-only surfaces promptly;
5. verify the privacy-minimized `ufanet_intercom_key_enrollment` result;
6. inspect live enrollment error behavior and any provider HTTP 400/status semantics;
7. after those gates are complete or explicitly waived, perform the final synchronized version/cache-bust bump across manifest, `INTEGRATION_VERSION`, base card version, **all frontend extension cache-busts**, and EN/RU README resource versions;
8. rerun Tests, HACS/Hassfest and Release self-check on the exact release-candidate SHA.

Do not merge, tag or publish from this draft without explicit approval after the remaining enrollment gates are complete or explicitly waived.
