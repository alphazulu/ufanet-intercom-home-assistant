# Ошибки и неподдерживаемое поведение

[English version](errors.md)

В этом разделе принципиально разделяются проверенные ошибки и просто неизвестное поведение.

## Прямой arbitrary MP4 из архива

**Статус: Not supported в проверенной форме**

```text
https://<MEDIA_SERVER>/<CAMERA_NUMBER>/archive-<START>-<DURATION>.mp4?token=<TOKEN_R>
```

Наблюдаемый результат: **HTTP 403**.

Вместо этого следует использовать archive HLS и remux через ffmpeg. См. [archive_RU.md](archive_RU.md).

## Неправильная схема Authorization

Ufanet и UCAMS используют разные схемы:

```text
Ufanet API: Authorization: JWT <UFANET_ACCESS>
UCAMS API:  Authorization: Bearer <UCAMS_TOKEN>
```

Подмена одной схемы другой является ошибкой клиента. Конкретная матрица HTTP status/body пока системно не собрана.

**Статус: схема авторизации Confirmed; детальные error response ещё документируются.**

## Истёкшие токены

Интеграция отслеживает время жизни токенов и обновляет/получает их заново. Точные ответы сервера для всех вариантов истечения токена пока не нормализованы в документации.

**Статус: рабочая логика Confirmed; детальные ошибки ещё предстоит собрать.**

## Архив ещё не сформирован

Сразу после realtime-события требуемый интервал после события может ещё отсутствовать в архиве. Поэтому автосохранение звонков в интеграции использует settle delay и повторные попытки.

Это стратегия интеграции, а не документированная гарантия Ufanet/UCAMS.

## Пустой `/api/v0/skud/`

На тестируемом аккаунте:

```http
GET /api/v0/skud/
```

вернул `[]`, тогда как:

```http
GET /api/v0/skud/shared/
```

вернул реальный домофон.

Пустой ответ `/api/v0/skud/` нельзя считать доказательством отсутствия домофонов.

## Ошибки регистрации физического ключа

Android-клиент содержит отдельную ветку для HTTP 400 при запуске `auto_collect/enable`, но точная server-side семантика status/body ещё не live-подтверждена проектом. Поэтому validation runtime не объявляет любой HTTP 400 конкретным provider status без реального наблюдения.

**Статус: Observed из Android-клиента; live error contract не подтверждён.**

## Неопределённый результат переименования физического ключа

`POST /api/v4/key/edit/` пока имеет статус **Observed**. Validation-service `rename_physical_key` не считает успешный POST достаточным доказательством нового имени: после write он перечитывает свежий inventory.

Если POST уже был отправлен, но последующий refresh завершился ошибкой, ключ исчез из свежего inventory либо новое имя не подтверждено, Home Assistant возвращает ошибку вида «ключ мог быть переименован, но результат не подтверждён». Это намеренно отличает неопределённый state-changing результат от доказанного failure/success и не запускает автоматический повтор POST, который мог бы дублировать пользовательское действие.

До реального ключа нельзя утверждать, какие HTTP status/body использует provider для invalid/stale key ID, duplicate name, ограничения длины или других rename errors.

## Как документировать новую ошибку

При новом наблюдении фиксируйте:

- endpoint и метод;
- обезличенный контекст запроса;
- HTTP status;
- обезличенное тело ответа;
- изменился ли результат после повтора;
- состояние/expiry токена без самого значения токена;
- наличие побочного эффекта;
- для write endpoint — удалось ли отдельно подтвердить итоговое состояние read-back запросом.

Не распространяйте один наблюдаемый status code на все ошибки без дополнительных подтверждений и не публикуйте provider key IDs/`external_id` в диагностических примерах.
